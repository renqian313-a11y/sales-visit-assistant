# 拜访助手 · 技术方案 v1.0

> 配套文档：PRD v1.0
> 本期范围：打透"拜访中"核心链路（F1 录音转写 → F2 总结 → F3 Todo → F4 话术）
> 端形态：移动端 H5（手机浏览器 / 微信内打开）
> 读者：产品负责人（非技术）+ 实现方

---

## 0. 一句话讲清楚这东西怎么跑起来

BD 用手机打开一个网页 → 点"开始拜访"并同意录音授权 → 边谈边录，录音每隔约 1 分钟自动悄悄上传 → 拜访结束点"完成" → 后台先把录音转成文字，再让 AI 一次性产出【总结 + Todo + 下次话术】→ 几秒后页面上就能看到结果，可微调后保存。

整条链路只有 4 个环节，下面逐个定清楚。

## 1. 技术架构总览

```
┌─────────────┐        ┌──────────────┐       ┌───────────────┐
│  手机 H5 页面 │  录音   │   后端服务     │ 文字  │   AI 大模型     │
│ (浏览器/微信) │ ─分段→  │ (接收/调度/存储) │ ──→  │ 总结+Todo+话术  │
└─────────────┘        └──────┬───────┘       └───────────────┘
      ↑                       │  音频
      │   结果展示              ↓
      └──────────────  ┌──────────────┐   ┌──────────────┐
                       │  对象存储(录音) │   │ 数据库(结构化) │
                       └──────────────┘   └──────────────┘
                              ↑
                       ┌──────────────┐
                       │  ASR 语音转写  │
                       └──────────────┘
```

四块拼图：
1. **前端 H5**：录音 + 上传 + 展示结果
2. **后端服务**：接收音频、调度 ASR 和 AI、存数据
3. **ASR**：把语音转成文字（外部云服务）
4. **LLM 大模型**：把文字变成总结/Todo/话术（外部云服务）

ASR 和 LLM 都是"买现成 API"，不用自己训练，这是 MVP 能一周做完的关键。

## 2. 核心链路时序（关键决策①：准实时，不做真实时）

PRD 写的是"实时/准实时"。这两条路架构差别很大：

| 方案 | 体验 | 复杂度 | 是否满足验收 |
|---|---|---|---|
| 真实时（边录边出字幕） | 拜访中能看到实时字幕 | 高（流式连接、断线重连复杂） | 超出需求 |
| **准实时（分段上传，结束后几秒出结果）** | 结束后立刻拿到总结 | 中等 | ✅ 验收只要求"结束后立刻拿到" |

**结论：本期做准实时。** 录音按约 60 秒切片，每片录完就后台上传转写；拜访一结束，把各片文字拼起来交给 AI，几秒出结果。

这样还顺带解决了弱网：每段独立上传，断了只重传那一段，不会丢整场录音。

## 3. 技术选型（每项给推荐 + 理由 + 大白话）

### 3.1 前端（H5）
- **录音能力**：用浏览器自带的 `MediaRecorder`。iOS 14.3+ 的 Safari 和微信内置浏览器都支持，覆盖绝大多数 BD 的手机。
- **大白话注意点**：网页录音**必须是 HTTPS**（带小锁的网址），否则浏览器不给开麦克风。所以上线要有个正经域名 + 证书。
- **本地缓存**：录音切片先存在手机本地（IndexedDB），上传成功再删，保证弱网/切后台不丢音。

### 3.2 ASR 语音转写（关键决策②）
门店环境吵、可能有方言、有行业黑话，识别率是生死线。推荐用**国内云厂商的"录音文件识别极速版"**（上传一段音频，1–2 秒返回文字）：

| 候选 | 特点 | 建议 |
|---|---|---|
| 火山引擎 ASR | 中文强、噪声鲁棒、速度快 | **首选** |
| 讯飞 ASR | 方言支持最全 | 备选（方言重的区域） |
| 阿里云 / 腾讯云 ASR | 成熟稳定 | 备选 |
| OpenAI Whisper | 便宜，但中文嘈杂场景一般、且数据出境有合规风险 | ❌ 不推荐本场景 |

> 待你确认：主要拜访区域有没有重方言？有的话优先讯飞。

### 3.3 LLM 大模型（做总结/Todo/话术）
关键技巧：**一次 API 调用，让模型同时吐出【总结+Todo+话术】三块结构化结果**（见第 5 节 Prompt），省钱省时。

| 候选 | 特点 | 建议 |
|---|---|---|
| 豆包 / DeepSeek | 便宜、中文好、够用 | **MVP 首选** |
| 通义千问-max / GPT / Claude | 质量更高、贵一些 | 质量不够时再升级 |

选型原则：MVP 先用便宜的跑通，验收发现总结质量不够再换更强的——**换模型只是改个配置，不用重写。**

### 3.4 后端服务
- 一个轻量服务即可（Node.js 或 Python）。只做三件事：收音频、调 ASR、调 LLM、存结果。
- MVP 阶段不需要复杂架构。

### 3.5 存储
- **录音文件**：放对象存储（火山 TOS / 阿里 OSS / 腾讯 COS），**加密存储**，满足合规（见第 6 节）。
- **结构化数据**（总结/Todo/话术）：MVP 用一个轻量数据库即可。

## 4. 数据结构定义（开发对齐的核心，必须先定）

一场拜访 = 一条 `VisitRecord`：

```json
{
  "id": "visit_001",
  "bd_user": "张三",
  "customer_name": "XX便利店",
  "store_type": "品牌 | 自助 | 线下",
  "start_time": "2026-06-29T10:00:00",
  "end_time": "2026-06-29T10:35:00",
  "consent": { "given": true, "time": "2026-06-29T10:00:01" },
  "status": "recording | transcribing | summarizing | done",
  "audio_url": "加密存储地址",
  "transcript": "全场拼接后的文字稿",

  "summary": {
    "customer_demands": ["客户诉求1", "诉求2"],
    "key_info": ["关键信息：报价/库存/竞品等"],
    "commitments": ["我方承诺：下周送样"],
    "risks": ["风险点：客户在比价竞品X"]
  },

  "todos": [
    { "content": "周五前寄样品", "owner": "张三", "due": "2026-07-03", "priority": "高" }
  ],

  "scripts": [
    { "scenario": "客户嫌贵", "suggested_line": "建议话术原文…", "rationale": "为什么这么说" }
  ]
}
```

这套字段就是前后端和 AI 输出的"合同"，定下来后大家照着做不会跑偏。

## 5. AI 提示词（Prompt）设计

一次调用产出三块。核心提示词骨架：

```
你是资深销售拜访助手。下面是一段 BD 与客户的拜访对话文字记录。
请严格按 JSON 输出，包含三部分：
1. summary：customer_demands / key_info / commitments / risks 四类要点
2. todos：待办事项，每条含 content / owner / due / priority
3. scripts：针对本次暴露的异议或机会，给出下次拜访话术 suggested_line 及 rationale
要求：只依据原文，不编造；信息不足的字段留空数组。

对话记录：
"""
{transcript}
"""
```

> 进阶（阶段二做）：把"历史话术库"也喂进去，让话术推荐基于团队沉淀，而不仅靠通用知识。

## 6. 合规与授权（不是一句话，是一个产品交互）

PRD 第 5 节提了合规，落到产品上必须做实：

1. **授权弹窗**：点"开始拜访"时，先弹"本次将录音用于生成拜访总结，是否同意"，记录 `consent`。没同意不给录。
2. **告知对方**：话术里提醒 BD 口头告知客户正在录音（不同地区法规不同，需告知）。
3. **脱敏存储**：手机号、身份证等敏感信息在存储/展示时做打码。
4. **加密 + 可删除**：录音加密存储，提供删除入口。

---

## 7. 弱网与缓存方案

- 录音按 60 秒切片，存本地 IndexedDB。
- 每片独立上传，失败自动重试，成功才删本地。
- 完全没网时：本地继续录，联网后按队列补传，再触发转写+总结。
- 保证："哪怕全程没信号，回到有网的地方也能出结果，绝不丢音。"

## 8. MVP 开发顺序（建议这样推进）

| 步骤 | 做什么 | 验证目标 |
|---|---|---|
| S1 | H5 能录音 + 分段上传 + 本地缓存 | 录音不丢、弱网能补传 |
| S2 | 接通 ASR，把音频转成文字 | 中文识别率达可用门槛 |
| S3 | 接通 LLM，文字 → 总结/Todo/话术 JSON | 输出结构正确、内容可用 |
| S4 | 结果展示页 + 可编辑 + 保存 | 总结可直接用于复盘 |
| S5 | 授权弹窗 + 合规 + 脱敏 | 满足合规底线 |
| S6 | 真人 BD 试用一周，收集用前/用后省时反馈 | 达成 PRD 验收标准 |

先把 S1→S4 这条"能跑通"的主干打通，再补 S5 合规和 S6 试用。
